# `.env` 方案规划（2026-09-22）

起因：hermes-lcm 的算法旋钮（`LCM_LEAF_CHUNK_TOKENS`、`LCM_FRESH_TAIL_COUNT`…）在上游只能用环境变量设，
misaka 没有 Hermes 那个 `~/.hermes/.env` 装载点，只能在 shell 里 export。问题于是变成：misaka 要不要有自己的
`.env`，如果有，边界画在哪。

## 一、现状：misaka 其实已经有四个"环境"

| 现有位置 | 装什么 | 谁写 | 登记/文档 |
|---|---|---|---|
| shell 环境 | `MISAKA_HOME`；插件 `LCM_*`；SDK 变量（`AZURE_OPENAI_*`、`GOOGLE_CLOUD_*`、`AWS_PROFILE`…）；**技能脚本要的第三方密钥**（继承 shell，减去黑名单） | 用户 | `MISAKA_HOME` 有文档，其余无 |
| `credentials/web.json` 的 `env` + settings.json `web.env` | web 层的供应商密钥 / 代理 / 端点，按名字形状分家（`is_credential_var`） | `misaka web setup` | 已登记、已文档 |
| `profiles/<role>/.skill-secrets.json` | 技能 `env_passthrough` 的密钥，`getpass` 逐个录入，0600 | `misaka skills …`（`operations.py:364`） | **未登记进布局表、未写进 CONFIGURATION.md**（真实 home 里目前没有实例） |
| 进程内部 `MISAKA_*` 管道 | 父进程交给子进程的身份/租约（`MISAKA_PROFILE_DIR`、`MISAKA_WHO`、`MISAKA_USAGE_*`、`MISAKA_SUBAGENT_*` 三十余个…） | 程序 | 内部协议 |

Hermes 只有两个：`~/.hermes/.env`（密钥 + 插件/SDK 变量，启动时装进进程环境，子进程继承）和 `config.yaml`。
`hermes setup` 把密钥写进 `.env`；技能脚本从同一份 `.env` 拿密钥（经 `env_policy` 过滤）。

pi 侧的密钥优先级（`auth_storage.getApiKey`）：运行时覆盖 > `auth.json` 里存的（api_key / oauth）> 环境变量
（`get_env_api_key`，如 `ANTHROPIC_API_KEY`）> fallback。所以环境变量本来就是 pi 认可的第三条路。

## 二、谁会用一个 `.env`（消费者盘点）

扫过 misaka 自己代码读的全部环境变量（vendor/native 除外）：`MISAKA_*` 97 个、第三方 34 个、终端/代理 15 个、
API 密钥 3 个；插件 `LCM_*` 约 50 个。按性质分四类：

1. **进程内部管道（约 60 个）——绝不能进 `.env`。** 写进去等于让每个进程都以为自己是某张卡。`MISAKA_HOME` 也不能：它决定 `.env` 在哪。
2. **本该是设置、今天只有环境变量一条路的自家旋钮（约 25 个）**：`MISAKA_PROVIDER/MODEL/LO_MODEL/FORCE_MODEL`（与 settings.json 的
   `defaultModel` / 角色钉**两套真值**）、`MISAKA_RESEARCH_PLAN_APPROVAL`、`MISAKA_MAX_CONCURRENT_SISTERS/_PER_SISTER`、`MISAKA_TOKEN_CAP`、
   `MISAKA_BEAST_AT`、`MISAKA_MCP_*_TIMEOUT`、`MISAKA_OCR_LANGS`、`MISAKA_PAGEINDEX`、`MISAKA_THEME`、`MISAKA_APP_TITLE`、`MISAKA_GHOSTTY_VT`、
   `MISAKA_SMALL_FAST_MODEL`、`MISAKA_MAX_CONCURRENT_SUBAGENTS`…——**该进 settings.json 的节**，不该进 `.env`（否则设置多第三个入口）。
   这是独立于 `.env` 的一项欠账，做不做 `.env` 都要做。
3. **真正属于"环境"的——被我们不控制的代码从进程环境里读的**：插件 `LCM_*`；SDK 变量；`LLAMA_BASE_URL`、`NOUS_*`、`MCP_OAUTH_*`；
   技能脚本要的第三方密钥；外部工具要的 `HTTPS_PROXY/SSL_CERT_FILE`。**这是 `.env` 的正当内容，也是全部内容。**
4. **诊断开关**：`MISAKA_TELEMETRY`、`MISAKA_TIMING`、`PI_EXPERIMENTAL`——留 shell。

## 三、方案 A：做 `.env`（Hermes 形，misaka 边界）

**文件**：`~/.misaka/.env`，布局表登记为 `env: Entry(".env", "edit", 0o600)`（用户编辑的东西住根目录；只是 owner-only）；`ensure()` 只收窄权限、从不创建；
拒绝符号链接；`strays()` 认识它；`uninstall` 删除；永不渲染给模型（`display()` 不会提到它的内容）。
角色覆盖：`profiles/<role>/.env`，同 `home.path("env", role)` 的覆盖语义（角色目录是 home 的局部覆盖）——
v1 可以先只做 home 级，覆盖是自然延伸。

**装载**：唯一装载点，在 `misaka/config/home.py`（或 `config/engine` 的进程入口）——每个 misaka 进程启动时、在任何代码读环境之前；
子进程（daemon、会话、卡片、DM）自然继承，不再各自装载。语义与 Hermes 一致：**shell 已有的变量不被覆盖**（shell > `.env`），
语法 = dotenv（`KEY=value`、引号、`#` 注释、可选 `export ` 前缀）；解析错误报行号、整文件拒绝，不半装。

**铁律：`.env` 不得设置任何 `MISAKA_*`。** 内部管道会被搞坏，自家旋钮要走 settings.json。装载器对 `MISAKA_*` 一律忽略并告警一次
（`MISAKA_HOME` 同样）。这一条把 ①② 两类挡在门外，只剩 ③。

**与现有存储的关系（不做兼容，一步收编）**：
- `credentials/web.json` 的 `env`（供应商密钥）→ 并入 `.env`；web 层改为从进程环境取密钥（仍按 `is_credential_var` 判定哪些名字是密钥、
  哪些是设置），settings.json `web.env` 只留代理/端点这类非密钥设置（现状已如此）。角色级供应商密钥 → `profiles/<role>/.env`。
- `profiles/<role>/.skill-secrets.json` → 并入 `profiles/<role>/.env`；`store_secret` 改写 `.env`；`load_env` 读进程环境 + 角色 `.env`。
  技能脚本拿到的仍经 `env_policy` 黑名单 + `env_passthrough` 白名单过滤——`.env` 里有 `FOO_API_KEY` 不等于技能能看见它。
- `auth.json` 不动：OAuth 会轮换的凭据不能放进手编文本文件。
- 转换脚本加第四阶段：把两个旧存储折进 `.env`（各角色一份），旧文件删除。

**子进程与安全**：DM 子进程、研究节点、卡片继承进程环境（现状）；技能脚本走 `execution_env(scrub=True)`；
`.env` 中的密钥不进 `settings.json`（0644）——`is_credential_var` 现在负责的那道分家仍然存在，只是密钥的落点从 `credentials/web.json` 变成 `.env`。

**测试**：解析（引号、注释、导出前缀、错误行）；不覆盖 shell；`MISAKA_*` 被忽略并告警；权限收窄；符号链接拒绝；
子进程继承；web 层从环境取密钥；技能 passthrough 从 `.env` 取；转换脚本折叠两个旧存储。

**文档**：CONFIGURATION.md 新节"`.env`：给不是 misaka 的代码用的环境"，README 配置表一行；`misaka setup` 后续可把 API 密钥写到这里（本期不做）。

**工作量**：核心装载器 + 布局表 + 测试约半天；web 与 skills 收编各半天；转换脚本与文档半天。风险集中在 web 层
（22 个测试文件刚按 `write_web` 改过，密钥落点再换一次要再过一遍）和 skills readiness（`.skill-secrets.json` 的读写路径）。

## 四、方案 B：不做 `.env`

- 插件 `LCM_*`：上游 `/lcm preset` 或 shell export。
- 技能密钥：保留 `profiles/<role>/.skill-secrets.json`，但**必须补登记进布局表、补文档**——它现在是个没人知道的秘密文件。
- SDK 变量：shell。
- ② 类旋钮迁 settings.json：照做。
- 代价：三个 env 形存储继续并存；从 Finder/launchd 起的 panel 拿不到 shell 里的密钥（技能会莫名失败）；与 Hermes 的差异保留。

## 五、推荐：A，附两个条件

理由：(1) 现状已经有三个 env 形的存储，收成一个正是这轮治理的方向；(2) 技能密钥今天靠 shell 是真实的脆弱点；
(3) 插件与 SDK 只认环境，绕不开；(4) 与 Hermes 的心智模型一致（`.env` = 密钥与外来变量，settings = 自家设置）。
条件：铁律"不放 `MISAKA_*`"写进装载器和文档；② 类迁移与之同期做，否则 `.env` 会被当成设置的后门。

不推荐的两个替代：给 settings.json `lcm` 节加 50 个键（偏离上游、新增配置面、而且这次的压缩根因不在旋钮）；
把 `leaf_chunk_tokens` 抬到 150k（关掉插件的核心特性）。

## 六、顺带发现（独立于 `.env`，见聊天记录 2026-09-22 晚）

1. **LCM 摄入了 misaka 自己的研究脚手架**：这次 25% 就压缩，47 条被摘掉的消息里 25 条 / 10k tokens 是进度 tick、阶段提示、
   纪律通知——模型每回合根本看不到它们（`research.context` 钩子剔掉），LCM 却把它们当对话归档并摘要；去掉后尾巴外只剩 11k < 20k，不会触发。
   修法：research 部件持久化这类条目时打**通用**"非对话记忆"标记，LCM 宿主 `ingest.upstream_messages` 跳过；
   顺带把插件里写死 `customType == "research-phase"` 的 `ingest.is_task_message` 改成读同一个通用属性（插件不该认识 research）。
   风险 B11 类（重放对齐、旧会话归档），动前重读 `align_sources`/checkpoint，带旧会话重开回归。
2. **压缩摘要走主模型，卡 113 秒**：`auxiliary.compression` 未配 → 用 gpt-6-astra high reasoning 做摘要。
   配置即可：`"auxiliary": {"compression": {"provider": "openai-codex", "model": "gpt-5.4-mini"}}`（同一 OAuth）。
3. `profiles/<role>/.skill-secrets.json` 未登记、未文档（方案 A 收编，方案 B 补登记）。
4. `MISAKA_PROVIDER/MODEL/LO_MODEL/FORCE_MODEL` 与 settings.json 双真值（② 类迁移的一部分）。
